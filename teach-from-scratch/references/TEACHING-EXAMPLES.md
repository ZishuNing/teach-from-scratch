# 讲法示例

用这些例子校准教学，不照抄句式。自然不等于随意，通俗不等于删掉机制；判断标准是读者能否跟着完成一次思考。

## 先有具体对象，再有名字

用户：“从零讲一下事件系统，会一点 C++。”

生硬的讲法：“事件系统是一种基于观察者模式的解耦机制，包含事件源、监听器和分发器三个核心组件。”

更合适的开头：

> 角色掉血时，血条要变短。先不用事件系统，扣血的函数直接调用血条的更新函数就能做到。
>
> 后来你还想播一个受伤音效。继续在扣血函数里加一行也能工作。不过，每增加一个反应，你都要回来修改扣血代码。
>
> 可以换个做法：血条和音效各自登记一个“掉血后要调用的函数”。扣血时只通知这份名单，让名单里的函数分别执行。这就是我们先做的最小事件系统。

到这里再给“订阅”“触发”的名字，并用 `100 → 80` 的血量跟一遍名单里的调用。等需要时再引入分发器，不立即列完整类图。说明这个最小版本的通知可以是同步调用，事件不天然等于异步。

## 沿同一个例子深入

用户：“为什么要缓存？别只讲定义。”

> 假设 `getPrice("A")` 要请求服务器。第一次查到 `20` 后，我们暂时把 `A → 20` 记在本地；紧接着再查 A，就能直接返回 `20`，省掉一次请求。这就是缓存。
>
> 麻烦在于，服务器稍后可能把价格改成 `25`。本地记录还在，但已经旧了。现在的问题变成了：这份记录什么时候还能用，什么时候必须重新查？
>
> 一种简单办法是同时记下查询时间，超过约定的有效期就重新请求。这叫过期策略。它减少了一直保留旧记录的机会，但不能保证有效期内价格绝不变化。

先看到一次请求如何省下来，再理解为什么不能永远复用。不要接着无差别列出缓存穿透、击穿、雪崩等名词；用户的目标需要时再展开。这里的 `20`、`25` 是教学设定，不是真实服务的观测结果。

## 听不懂时补中间一步

用户：“还是不懂引用，能再白话一点吗？”

不只改成：“引用本质上就是别名，你可以把它理解为另一个名字。”

换一个可以逐行看的局部代码片段，不把它称为已运行的完整程序：

```cpp
int a = 3;
int& b = a;
b = 8;
```

> 先看第一行：有一个整数变量 `a`，值是 `3`。
>
> 第二行没有复制出另一个整数。通过 `b` 访问的，仍是 `a` 所表示的同一个对象。
>
> 所以第三行通过 `b` 改值后，读 `a` 会得到 `8`。如果第二行换成 `int b = a;`，才是复制出独立的变量，之后改 `b` 不会改 `a`。

如果用户继续追问存储或实现，再区分 C++ 的语言语义与编译器实现；不要把“引用永远不占内存”当成上述例子的结论。需要确认卡点时问“是不清楚第二行有没有复制，还是不清楚第三行为何影响 a？”，不用泛泛地问“懂了吗”。

## 不靠制造故障推动每一课

用户：“我懂二维坐标了，接下来讲三维。”

> 二维里用两个数表示位置，比如 `(2, 3)`。如果还需要区分高度，就再加一个数：`(2, 3, 5)`。前两个数不变，第三个数告诉我们它在所选高度轴上的位置。

新目标本身就能引出新概念，无需宣称二维坐标“失败了”。接着结合实际系统说明哪条轴表示高度；不能默认所有引擎都用相同轴向。

## 对部分正确的回答给具体反馈

用户：“缓存就是把数据存起来，所以之后都不用重新算。”

> 前半句抓到了：把结果留着，后面可以复用。“之后都不用”还需要一个条件：影响结果的输入没有变，而且记录仍然有效。像刚才的价格例子，服务器改价以后，本地那份 `20` 就不能一直当作当前价格。

纠正过度概括，保留已经理解的部分。不先说“完全正确”，也不为了鼓励而放过错误。是否接着让用户再试一个例子，取决于他是否愿意练习。

## 什么都不会时，先给一小段可见的收获

用户：“从零教我做一个待办列表，不知道选什么技术。”

可以先讲：“先把一个待办看成两项信息：要做的事，以及有没有做完。例如‘买牛奶，未完成’。把几条这样的记录放在一起，就是最初的数据。下一步才是让你能添加一条记录。”

若要进入实际开发，再问运行在哪里这类会改变实现的问题。不要先让用户选择所有框架、架构分层、练习模式和课程档位。已经明确的平台和基础不要重问。
